農業OS：開発・運用ロードマップ

更新：2026年11月4日 ／ 次に取り組む候補と、実装前に議論すること。

機能を増やすこと自体を目的にせず、毎日の手間を減らすことと、収益につながる判断を良くすることを重視する。

予定 → 連絡 → 作業ログ → 日誌の基盤は運用しながら改善する。以下は開発予定の整理であり、未実装機能の利用開始や期限を約束するものではない。

直近の4テーマ

  1. LINE Bot連携：着手候補。毎日の連絡の手間を減らす。
  2. 日々の記録の集計・振り返り：要議論。作業時間・段取り・人員配置を改善する。
  3. 保存画像の活用：要議論。生育変化の比較と現場確認に役立てる。
  4. 支出・原価・概算収支の把握：要議論。農園全体と圃場・作付けの採算を考える。

2〜4は、判断したいこと → 必要な記録・計算方法 → 小さく試す → 効果を確認、の順で進める。並び順は実装順の確定ではなく、集計と収支は重なる部分を共通化する。

1. LINE Bot連携

状態：着手候補（送信方法・宛先の確認から）

今ある業務連絡の文面生成・共通連絡・控えを生かし、コピーしてLINEへ貼り付ける手間を減らす。

最初の範囲

  • 作業者とLINEの宛先を安全に紐づけ、管理者が送信先・文面を確認してから送る。
  • 勤務時間や参加作業が違う人には、それぞれの連絡文を送る。共通の注意事項や手修正も保持する。
  • 送信結果と当時の予定・文面を控えに残し、予定変更時の再連絡の判断につなげる。

実装前に決めること

  • 個人宛て／グループ宛て、友だち追加・本人確認・宛先変更の運用。
  • 送信権限、料金・通数上限、失敗時の再試行と二重送信防止。手動コピーの導線は残す。
  • コピー済み・送信API受付・既読は区別する。自動定時送信や返信受付は初期範囲に含めず、必要性を別途検討する。

確認する効果：連絡にかかる時間が減り、誤送信・送信漏れ・重複送信を防げるか。

2. 日々の記録の集計・振り返り

状態：判断したいこと・集計単位を議論

「どの作業・圃場に時間がかかっているか」「次回の段取りや人の配置をどう変えるか」を、記憶だけでなく記録から考える。

最初の範囲の候補

  • 日誌・作業ログを週・月・作業・圃場・作付けで振り返り、元の記録へ戻れるようにする。
  • 作業時間、延べ人数時間、作業量・面積を整理し、記録が揃うものから単位面積・出荷重量あたりの作業負担を見る。
  • 予定と実績の違いや、天候・予定外作業のメモを改善の材料にする。予定を実績として自動計上しない。
  • 既存の収穫KPIなどを生かし、同じ集計画面を重複して作らない。

先に確認すること

  • 記録時刻と作業開始・終了は別。時間不明は不明とし、未記録を作業なし・0時間にしない。
  • 同時施肥・共同作業・重複時間・休憩・複数圃場への時間配分をどう扱うか。作業時間と人数分の労働時間を混同しない。
  • 面積・収量の単位と対象期間を合わせ、品種・作期・天候・機械など条件の違いを見て比較する。
  • 誰の評価をするかではなく、どの作業を改善するかを起点にする。集計のためだけの入力負担を増やしすぎない。

小さな検証：一つの作業を選び、元ログと集計を照合 → 段取りを一つ変える → 次回の時間・負担を比べる。

確認する効果：集計を見ることで具体的な改善を選べるか。記録・確認の手間以上の価値があるか。

3. 保存画像のさらに効果的な活用

状態：比較したい場面・撮影運用を議論

保存写真を「探して見る」だけでなく、同じ作付けの変化や、問題発生前後を振り返る材料にする。

最初の範囲の候補

  • 圃場・作付け・撮影日で絞り、同じ作付けの写真を時系列や2枚並列で比較する。
  • 定植後の日数、撮影メモ、関連する施肥・防除などの記録を確認できるようにする。
  • 全体写真で生育・被害の広がりを、接写で病斑・虫・葉裏の細部を残す。同じ位置・向き・距離での定点撮影も試す。

先に確認すること

  • 生育の遅れ、病害虫、処置前後など、何を比較してどんな現地確認・判断につなげたいかを選ぶ。
  • 日付・作付けの紐づけ、撮影角度・光・距離の違いを考慮する。見た目の違いだけで原因や効果を断定しない。
  • 現在は縦横比を保ち長辺1920px以下のJPEGへ縮小・圧縮して保存する。細部は別の接写やアップロード前の原画像の切り抜きで残し、必要なら原本保存も検討する。
  • AIによる診断・収量推定を先に目的化しない。導入する場合は精度検証・費用・画像の外部送信と取扱いを別途確認する。

小さな検証：一つの作付けで写真を継続し、過去との比較が生育変化の把握・現地確認に役立つか試す。

確認する効果：必要な写真をすぐ探せ、変化に気づけるか。撮影・整理の負担に見合うか。

4. 支出・原価・概算収支の把握

状態：費用の範囲・単価・配分方法を議論

JA経費分析を出発点に、他社への支払いや大きな買い物も把握し、圃場・作付けの採算を考える。まずは経営判断用の概算とし、会計・税務上の利益や預金残高とは区別する。

段階A：他社請求書PDFの保存と支出一覧

  • 紙で届く他社請求書をPDF化して非公開保存し、取引先・日付・金額・分類・支払状況・メモを登録する。
  • JA分と合わせて月別・費目別の支出や、農機・設備・修理など大きな買い物の原本を確認する。
  • 帳票ごとに形式が異なるため、最初から全社の自動解析を前提にしない。手入力・確認修正を用意し、画像PDFのOCRは精度と費用を検証する。
  • 請求書・領収書・JA明細に重複する取引や、再アップロードを二重計上しない方法を決める。

段階B：圃場・作付けごとの肥料代・農薬代

  • 購入情報の資材名・規格・内容量・価格と、作業ログの使用量を接続し、「使用量 × 単価」で概算する。
  • 肥料の袋・kg、農薬の容器容量・原液量・希釈倍率・散布液量を区別して換算する。単価・量が不明な記録は未算出として見せる。
  • 購入時期で異なる単価、在庫・繰越、複数圃場への配分、作付け前の土づくり費用の扱いを決める。
  • 購入額は支出、使った分は栽培原価として分け、同じ資材費を二重に加算しない。

段階C：人件費・概算売上との接続

  • 実際の作業時間・人数と適用時給から雇用人件費を概算する。シフト・予定時間をそのまま実績にしない。通勤費などの含有範囲も決める。
  • 家族労働の評価額は、実際に支払う雇用人件費と別表示にする。圃場を特定できない共通作業や費用は無理に配分しない。
  • 契約出荷は「対象の出荷実績kg × 契約単価」で概算売上を計算する。収穫量ではなく出荷量を使い、契約・適用期間・規格・返品等を確認する。
  • 複数圃場の混載出荷をどう紐づけるか検討し、不明分は農園全体に残す。JA販売伝票を取り込む場合は概算との照合・置換とし、重複加算しない。

表示と判断のルール

  • まずは「概算売上 − 把握できた資材費・雇用人件費」を表示し、最終利益とは呼ばない。未計上・未配分・推定値を明示する。
  • 農機購入などの現金支出と、減価償却・複数作にまたがる原価配分を区別する。税・手数料・運賃・燃料・地代等をどこまで含めるかも決める。
  • 請求書・単価・人件費は非公開で、既存の認証・権限管理を生かす。公開データへ混ぜない。

小さな検証：他社請求書の保存を入口に、一つの作付け・主要資材で手計算と照合し、分からない費用を洗い出す。

確認する効果：何に支出し、何の原価が高いかを説明できるか。来作の品種・圃場・規模・作業方法の判断に使えるか。

進め方と着手の目安

  1. 今の予定 → 連絡 → 作業ログ → 日誌を日々使い、残る手間や記録の不足を確認する。
  2. LINE Botは宛先・送信運用を決めたうえで、小さな範囲から着手する。
  3. 残る3テーマは一度に作らず、最初に良くしたい判断を一つ選び、計算方法・入力負担・費用を議論する。
  4. 既存記録で小さく検証し、手計算・元記録との一致と、実際の改善効果を確認してから広げる。
実現済みの基盤（新規タスクから外したもの）

以下は基盤として実装済み。分析や運用の完成を意味するものではなく、今後は上のテーマから必要な改善を選ぶ。

  • 施肥・防除などの作業ログと、圃場ごとの管理作業履歴・回数の確認。費用との接続はテーマ4に残す。
  • 播種・定植・収穫・出荷の記録と作付けの参照、既存の圃場・品種別サマリー。育苗専用の追加機能や高度な比較分析は別途検討する。
  • 気象・積算温度の表示基盤。収穫日・反収との関係の検証や予測精度の評価は今後の課題。
  • 日別予定の作成・編集、勤務・参加時間別の連絡文、共通連絡の追記、コピー控えと予定変更の確認。
  • 作業ログを基本にした日誌、予定と実績の参照、必要な時間修正・予定外作業・メモの補足。
  • 圃場・作付けに紐づく写真の保存・一覧・閲覧と、JA請求書PDFの取り込み・分類・月別経費分析。
中長期候補（旧ロードマップから保留・統合）
  • 品種・圃場・作期の比較：反収の安定性、面積との関係、育苗日数・施肥量・防除回数との比較はテーマ2へ統合。採算比較はテーマ4へつなぐ。散布図を作ること自体を目的にせず、データ量と比較条件を確認する。
  • 育苗管理の追加：発芽率・ロット・育苗中の作業など、既存の播種・定植記録で不足する項目が判断に必要かを確認してから追加する。
  • 気象・生育予測：気象・積算温度と実際の生育・収穫を照合する。NARO等のモデルは対象作物・利用条件・自園での精度を検証してから検討し、病害虫・施肥適期・収量を予測できると先に断定しない。
